## 3. What is complete, and what each piece contributes

### 3.1 M0: Foundation (Phase 0)

| Completed | Where | What it contributes |
|---|---|---|
| Typed configuration with validation | `internal/platform/config` | Every service reads its settings the same way and fails fast on bad values |
| Structured JSON logging with request IDs | `internal/platform/logging` | Any request can be followed through the logs |
| HTTP toolkit: router with route labels, middleware chain, RFC 9457 errors, strict JSON, graceful shutdown, admin router | `internal/platform/httpx` | Services share one safe HTTP stack; errors have stable codes; internal endpoints stay off the public port |
| Health checks with draining (`/livez`, `/readyz`) | `internal/platform/health` | Pods stop receiving traffic before shutdown, so in-flight requests finish |
| Prometheus metrics registry | `internal/platform/metrics` | The data behind dashboards, alerts and published numbers |
| Ed25519 admission tokens with key rotation | `internal/platform/authn` | Only admitted buyers can hold seats; keys rotate without downtime |
| PostgreSQL pool and embedded migration runner (advisory lock, checksums) | `internal/platform/postgres`, `db/migrations` | Schema changes are applied safely and applied migrations can't be edited |
| Valkey client | `internal/platform/valkey` | Connection to the hot-path store, Sentinel-ready for Phase 5 |
| Component lifecycle and build info | `internal/platform/app`, `buildinfo` | Clean start and stop for every service; every binary reports its version |
| Makefile, `compose.yaml`, Dockerfile, GitHub Actions CI, golangci-lint, pre-commit hooks, migration check script | Repository root, `.github/`, `scripts/` | One-command local stack; every push is linted, tested and checked by E1 |
| `README.md`, `AGENTS.md`, `CONTRIBUTING.md`, `docs/architecture.md`, ADRs 0001 and 0003 | Repository root, `docs/` | New contributors and AI agents know the rules and the system map |

### 3.2 M1: Correctness core (Phase 1)

| Completed | Where | What it contributes |
|---|---|---|
| Five atomic Lua scripts: `provision`, `hold`, `mark_paying`, `release`, `confirm` | `internal/inventory/scripts` | **I1 no oversell** on the hot path: check and decrement happen in one step, with no locks |
| inventory-svc: store, service, HTTP handler, metrics | `cmd/inventory`, `internal/inventory` | Buyers can hold, read and cancel seats; retries are safe through `Idempotency-Key` |
| Expiry sweeper, safe in every replica | `internal/inventory/sweeper.go` | **I5 no lost units:** expired holds always return to the pool |
| Per-user counter inside `hold.lua` | `internal/inventory/scripts/hold.lua` | **I4 per-user cap** on the hot path |
| Late-confirm handling | `internal/inventory/scripts/confirm.lua` | A payment that arrives after expiry still becomes a sale instead of being lost |
| PostgreSQL final guard: conditional `UPDATE`, conditional upsert, `no_oversell` CHECK | `internal/booking/guard`, `db/migrations/booking/00001` | **I1 and I4** enforced by the source of truth, whatever the fast path believes |
| Event catalog | `internal/booking/catalog` | Events exist in PostgreSQL, the system of record |
| `holdfastctl`: migrate, keys, token mint, event create, inventory provision and status | `cmd/holdfastctl` | Operators can set up events and rebuild Valkey from PostgreSQL |
| Experiment E1: 50,000 buyers for 1,000 units, plus 10,000 concurrent confirmations through the guard | `cmd/contention` | The no-oversell claim is tested on every CI run, and any regression fails the build |
| 58 test functions, including a seeded, model-based randomized test of 1,500 operations | `*_test.go` | Logic, storage and concurrency are checked against a simple model of the rules |
| Grafana inventory dashboard and Prometheus scrape config | `deploy/` | Live view of holds, availability and latency |
| Service doc, runbooks RB-INV-1 to RB-INV-6, ADRs 0002 and 0004 | `docs/` | The API, error codes and failure handling are written down |
